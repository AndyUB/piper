4. ANALYSIS & ASSESSMENT
──────────────────────────────────────────────────────────────────────────────

A. Is 72-73% scaling efficiency reasonable?
   YES. Sources of overhead:
   - PP bubble: interleaved-1f1b with pp=2, mbs=4 → bubble ratio = (pp-1)/(mbs+(pp-1)) = 1/5 = 20%
     (interleaved schedule reduces this further, but it's still non-zero)
   - DP all-reduce / ZeRO RS+AG: adds latency on comm_stream (overlapped but not zero-cost)
   - P2P communication between PP stages
   - The single-GPU baseline uses mbs=1 (less GPU utilisation) which inflates the
     single-GPU per-GPU number, making scaling efficiency look worse than it is.

B. Why is ZeRO-3 the fastest, not the slowest?
   ZeRO-3 adds all-gather per bucket before each FWD. However all 36 AGs per stage are
   dispatched as DAG root nodes and queued on comm_stream before any FWD compute starts.
   Each FWD_b waits (GPU-side) only for AG_b; while FWD_b runs on comp_stream, AG_{b+1..N}
   run concurrently on comm_stream. The AG GPU time (~0.3ms each) is fully hidden behind
   FWD compute. The ~1% ZeRO-3 speedup over dp-nozero is within run-to-run variance but
   may reflect GPU memory access patterns improving when params are loaded bucket-by-bucket.
   ZeRO-3 also shows the lowest variance (±0.025s), suggesting more stable execution.

C. Why are ZeRO-1/2/3 all showing identical memory breakdown?
   bucket_flat_params and bucket_flat_grads are full reconstruction buffers present at
   all ZeRO levels (needed for FWD/BWD compute). ZeRO-2 shards *where gradients land*
   (in bucket_rs_grads, a smaller buffer), but flat_grads is still fully allocated.
   ZeRO-3 reconstructs full params from shard each iteration. The visible difference is:
   - shard (1.680 GiB) present for ZeRO-1/2/3, absent for ZeRO-0 — this is the
     optimizer's working set; Adam momentum+variance live alongside it
   - "other" 1.68 GiB lower for ZeRO-1/2/3, consistent with halved optimizer buffers

D. Peak vs allocated gap is large (e.g. 39.1 GiB peak vs 11.9 GiB allocated for ZeRO-1):
   The gap (~27 GiB) is dominated by:
   - All microbatch activations alive simultaneously during backward pass
     (seq=256, mbs=4, interleaved schedule: multiple forward passes before backward)
   - PyTorch allocator retains reserved memory even after tensors are freed
   - Gradient computation graph held in memory until optimizer.zero_grad()

──────────────────────────────────────────────────────────────────────────────
5. RECOMMENDATIONS
──────────────────────────────────────────────────────────────────────────────
1. Activation checkpointing: the 27 GiB activation footprint dwarfs param/grad memory.
   Enabling --activation-checkpointing would reduce peak dramatically (at ~33% compute cost).

2. Larger microbatch size or more microbatches: reduces PP bubble ratio, improves
   GPU utilisation, and may improve scaling efficiency toward ~85-90%.

3. Bucket count reduction: currently 36 buckets/stage. Fewer, larger buckets would
   reduce NCCL call overhead (currently 72 NCCL calls/iter for ZeRO-3 per rank).
   Target 4-8 buckets for a better compute-communication granularity tradeoff.

4. ZeRO-3 is already as fast as ZeRO-0 here — the bucketed prefetch design works well.
   For larger models or longer sequences where activation memory is less dominant,
   ZeRO-3's parameter savings would become the deciding factor.

8. ADDITIONAL ANALYSIS
──────────────────────────────────────────────────────────────────────────────

E. Non-bucketed vs bucketed throughput (PP=2, note: different GPUs so absolute values differ):
   Bucketed (Run 1) showed: zero-3 fastest, zero-1 slowest (-1.4% vs dp-nozero).
   Non-bucketed (Run 2) shows: zero-2 fastest (+4.8%), zero-1 slightly slower (-1.0%).
   Zero-3 without bucketing no longer leads — without the prefetch overlap mechanism,
   the ZeRO-3 all-gather overhead is not hidden and it performs similarly to ZeRO-0.
   Zero-2 leading non-bucketed is surprising and likely within variance (±0.10s std).

F. Why did zero-3_nopp OOM, and was it expected?
   NOT expected. The ZeRO-3 all_gather writes into the pre-allocated bucket_flat_params
   buffer (piper_actor.py:1646) — it does not allocate any extra tensor. So zero-3_nopp
   memory footprint = zero-1/2_nopp = 52.373 GiB, well within the 139.81 GiB GPU.
   The actual OOM showed "Process 3860681 has 131.07 GiB memory in use" — a stale Ray
   worker from previous runs holding GPU memory across sessions. Re-running on clean
   GPUs 2,3 succeeded with peak = 52.373 GiB as predicted.

G. Why are ZeRO-1/2 ~13% faster than dp-nozero with no-PP?
   With no-PP, the all-reduce (dp-nozero) is a single coarse-grained NCCL op launched
   after the entire backward pass completes, giving zero overlap with computation.
   ZeRO-1/2's post_accumulate_grad_hook fires per-parameter as each gradient becomes
   ready during backprop, launching reduce-scatter immediately. This provides fine-
   grained comm/compute overlap that the monolithic all-reduce cannot.
   With PP=2 this advantage is smaller (ZeRO-1 is still −1% vs dp-nozero) because the
   pipeline schedule already creates compute/communication concurrency via the DAG
   task graph; ZeRO hooks add marginal benefit on top.
   Implication: for single-node DP without PP, switching from DDP all-reduce to ZeRO-1/2
   can yield meaningful speedup through better overlap, even without bucketed prefetch.
   ZeRO-3 with no-PP is only +4.2% vs dp-nozero because the AG overhead (0.105s, ~30 GB/s
   × 3.36 GiB) is not overlapped with any compute — it partially cancels the RS benefit.
   The AG cost with no-PP and no bucketed overlap is: 1.231 - 1.126 = 0.105s vs zero-1.
   This contrasts sharply with PP=2 where ZeRO-3 matches ZeRO-0 (AGs fully hidden).

10. no-pp zero-3 OOM ANALYSIS
──────────────────────────────────────────────────────────────────────────────

Cause: NOT a memory capacity problem. The OOM error shows:
  "GPU 0 has a total capacity of 139.81 GiB of which 210.88 MiB is free.
   Process 3860681 has 131.07 GiB memory in use."

  Process 3860681 is a Ray worker from the preceding zero-2_nopp session that
  did not fully release GPU memory before zero-3_nopp launched. 131 GiB from a
  single process is far more than any one run uses (peak ≈ 52 GiB), indicating
  memory accumulated across the entire sequential chain of Ray sessions.

Expected memory for zero-3_nopp under clean conditions:
  bucket_flat_params is always allocated at full size and persists the entire
  iteration (piper_actor.py:842). ZeRO-3 all_gather writes INTO this existing
  buffer (piper_actor.py:1646) — it does NOT allocate a new temporary tensor.
  Therefore zero-3_nopp peak ≈ zero-1/2_nopp peak ≈ 52.373 GiB << 139.81 GiB.

12. WHY BUCKETING IS SLOWER
──────────────────────────────────────────────────────────────────────────────

Observed overhead (Run 1 bucketed vs Run 2 non-bucketed, PP=2):

  Config      Bucketed   Non-bucketed   Overhead
  ──────────  ────────   ────────────   ────────
  dp-nozero   2.891s     2.431s         +18.9%
  zero-1      2.940s     2.457s         +19.7%
  zero-2      2.924s     2.320s         +26.0%
  zero-3      2.863s     2.428s         +17.9%

Hardware is not a confound: single-GPU baselines are 1.054s (Run 1) vs 1.057s (Run 2),
a difference of +0.28%. The 18-26% overhead is due to bucketing, not the GPU assignment.
The overhead is also present for dp-nozero (no ZeRO comms), confirming it is not specific
to gradient communication.

Why bucketing adds overhead:

1. Python scheduler overhead per bucket sub-task (dominant)
   ─────────────────────────────────────────────────────────
   expand_bucket_tasks() replaces each FWD/BWD task with a chain of K=36 bucket nodes.
   For PP=2, interleaved-1F1B, MB=4: 16 compute tasks/rank → 576 bucket sub-tasks/rank.
   The run_dag() Python scheduler processes each node: in_degree tracking, queue management,
   CUDA event creation (torch.cuda.Event()), event recording, and stream.wait_event() calls.

   Quantifying this: dp-nozero overhead = 2.891 − 2.431 = 0.460s across 560 extra compute
   nodes + 70 extra AR nodes = 630 extra tasks, giving ~0.73 ms overhead per extra task.
   At K=36 and 2.4ms actual compute per bucket (88ms/stage ÷ 36), Python/CUDA dispatch
   overhead is ~30% of compute per bucket, which directly produces ~19% total overhead.

2. Compute fragmentation — buckets are sub-layer granularity
   ────────────────────────────────────────────────────────────
   LLaMA-3B has ~28 transformer layers split across 4 FX stages (7 layers/stage). With
   36 buckets/stage, each bucket covers ~0.19 layers of compute. At this granularity:
   - GPU arithmetic units are underutilised: small work units don't fill the GPU's
     warp scheduler; each kernel launch has a ~5-20μs startup dead-time.
   - More autograd graph segments: each bucket's backward is a separate autograd call,
     increasing graph traversal overhead and gradient accumulation bookkeeping.
   - Intermediate tensor materialisation at every bucket boundary: outputs of bucket b
     are stored in bucket_buffer before being passed as inputs to bucket b+1, adding
     memory writes/reads that are absent in the single-pass non-bucketed case.

3. 36× more NCCL operations (same bytes, higher per-call overhead)
   ─────────────────────────────────────────────────────────────────
   Non-bucketed: 1 all-reduce per stage per rank (∼3.36 GiB per call for dp-nozero)
   Bucketed:     36 all-reduces per stage per rank (∼93 MB each)
   Total gradient bytes are identical; bandwidth utilisation is similar (93 MB is still
   bandwidth-bound at 30 GB/s). The overhead comes from NCCL's fixed per-call cost:
   host-side enqueue, internal ring-buffer write, and GPU-side kernel setup. At 36×
   more calls per stage × 2 stages = 72 extra NCCL calls per rank this adds up.

4. More CUDA events (36× event create + record + wait chains)
   ───────────────────────────────────────────────────────────
   Each bucket sub-task records a CUDA event on comp_stream after executing, and the
   next sub-task (or the AR node) waits on that event. With 576 sub-tasks vs 16 original
   tasks, there are 560 extra event create/record/wait triples per rank per iteration.
   Each triple involves a GPU operation (timestamp + dependency insertion), adding small
   but compounding overhead.

5. Zero-2 outlier (+26% vs +18% for others)
   ──────────────────────────────────────────
   Non-bucketed zero-2 was unusually fast (2.320s, +4.8% vs dp-nozero, best config).
   Bucketed zero-2 is 2.924s, barely faster than bucketed zero-1 (2.940s). The benefit
   that made non-bucketed zero-2 stand out — likely a favourable timing alignment between
   RS communication and the pipeline's bubble slots — is disrupted by bucketing. The
   fine-grained bucket chain serialises the backward pass differently, eliminating the
   overlap window that zero-2's RS timing was exploiting.

Summary:
  The 36-bucket design was motivated by prefetch overlap for ZeRO-3 (AG for bucket b+1
  fires while FWD for bucket b runs) and fine-grained RS overlap for ZeRO-1/2. In
  practice, the Python scheduler + CUDA event overhead per bucket (~0.73ms) consumes
  ~30% of each bucket's compute time (2.4ms), drowning out the overlap benefit.
  The design would perform better with fewer, larger buckets (4-8 instead of 36)
  to amortise Python/CUDA overhead across more GPU work per bucket.

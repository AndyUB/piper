──────────────────────────────────────────────────────────────────────────────
4. ANALYSIS & ASSESSMENT
──────────────────────────────────────────────────────────────────────────────

A. Is 72-73% scaling efficiency reasonable?
   YES. Sources of overhead:
   - PP bubble: interleaved-1f1b with pp=2, mbs=4 → bubble ratio = (pp-1)/(mbs+(pp-1)) = 1/5 = 20%
     (interleaved schedule reduces this further, but it's still non-zero)
   - DP all-reduce / ZeRO RS+AG: adds latency on comm_stream (overlapped but not zero-cost)
   - P2P communication between PP stages
   - The single-GPU baseline uses mbs=1 (less GPU utilisation) which inflates the
     single-GPU per-GPU number, making scaling efficiency look worse than it is.

B. Why is ZeRO-3 the fastest, not the slowest?
   ZeRO-3 adds all-gather per bucket before each FWD. However all 36 AGs per stage are
   dispatched as DAG root nodes and queued on comm_stream before any FWD compute starts.
   Each FWD_b waits (GPU-side) only for AG_b; while FWD_b runs on comp_stream, AG_{b+1..N}
   run concurrently on comm_stream. The AG GPU time (~0.3ms each) is fully hidden behind
   FWD compute. The ~1% ZeRO-3 speedup over dp-nozero is within run-to-run variance but
   may reflect GPU memory access patterns improving when params are loaded bucket-by-bucket.
   ZeRO-3 also shows the lowest variance (±0.025s), suggesting more stable execution.

C. Why are ZeRO-1/2/3 all showing identical memory breakdown?
   bucket_flat_params and bucket_flat_grads are full reconstruction buffers present at
   all ZeRO levels (needed for FWD/BWD compute). ZeRO-2 shards *where gradients land*
   (in bucket_rs_grads, a smaller buffer), but flat_grads is still fully allocated.
   ZeRO-3 reconstructs full params from shard each iteration. The visible difference is:
   - shard (1.680 GiB) present for ZeRO-1/2/3, absent for ZeRO-0 — this is the
     optimizer's working set; Adam momentum+variance live alongside it
   - "other" 1.68 GiB lower for ZeRO-1/2/3, consistent with halved optimizer buffers

D. Peak vs allocated gap is large (e.g. 39.1 GiB peak vs 11.9 GiB allocated for ZeRO-1):
   The gap (~27 GiB) is dominated by:
   - All microbatch activations alive simultaneously during backward pass
     (seq=256, mbs=4, interleaved schedule: multiple forward passes before backward)
   - PyTorch allocator retains reserved memory even after tensors are freed
   - Gradient computation graph held in memory until optimizer.zero_grad()

──────────────────────────────────────────────────────────────────────────────
5. RECOMMENDATIONS
──────────────────────────────────────────────────────────────────────────────
1. Activation checkpointing: the 27 GiB activation footprint dwarfs param/grad memory.
   Enabling --activation-checkpointing would reduce peak dramatically (at ~33% compute cost).

2. Larger microbatch size or more microbatches: reduces PP bubble ratio, improves
   GPU utilisation, and may improve scaling efficiency toward ~85-90%.

3. Bucket count reduction: currently 36 buckets/stage. Fewer, larger buckets would
   reduce NCCL call overhead (currently 72 NCCL calls/iter for ZeRO-3 per rank).
   Target 4-8 buckets for a better compute-communication granularity tradeoff.

4. ZeRO-3 is already as fast as ZeRO-0 here — the bucketed prefetch design works well.
   For larger models or longer sequences where activation memory is less dominant,
   ZeRO-3's parameter savings would become the deciding factor.

8. ADDITIONAL ANALYSIS
──────────────────────────────────────────────────────────────────────────────

E. Non-bucketed vs bucketed throughput (PP=2, note: different GPUs so absolute values differ):
   Bucketed (Run 1) showed: zero-3 fastest, zero-1 slowest (-1.4% vs dp-nozero).
   Non-bucketed (Run 2) shows: zero-2 fastest (+4.8%), zero-1 slightly slower (-1.0%).
   Zero-3 without bucketing no longer leads — without the prefetch overlap mechanism,
   the ZeRO-3 all-gather overhead is not hidden and it performs similarly to ZeRO-0.
   Zero-2 leading non-bucketed is surprising and likely within variance (±0.10s std).

F. Why does zero-3_nopp OOM while zero-1/2_nopp do not?
   At the start of each forward pass ZeRO-3 must all-gather the full parameter tensor
   (6.718 GiB) as a temporary reconstruction buffer alongside the existing params.
   With no-PP, the full 6.718 GiB params are already on each rank (no PP split), so
   ZeRO-3 transiently needs ~2× params ≈ 13.4 GiB extra vs zero-1/2. Combined with the
   ~52 GiB already in use (from zero-1/2_nopp baseline), this pushes past the GPU's
   capacity. The Run 2 OOM was also aggravated by stale memory from the previous Ray
   session not fully releasing before the zero-3_nopp process started.

G. Why are ZeRO-1/2 ~13% faster than dp-nozero with no-PP?
   With no-PP, the all-reduce (dp-nozero) is a single coarse-grained NCCL op launched
   after the entire backward pass completes, giving zero overlap with computation.
   ZeRO-1/2's post_accumulate_grad_hook fires per-parameter as each gradient becomes
   ready during backprop, launching reduce-scatter immediately. This provides fine-
   grained comm/compute overlap that the monolithic all-reduce cannot.
   With PP=2 this advantage is smaller (ZeRO-1 is still −1% vs dp-nozero) because the
   pipeline schedule already creates compute/communication concurrency via the DAG
   task graph; ZeRO hooks add marginal benefit on top.
   Implication: for single-node DP without PP, switching from DDP all-reduce to ZeRO-1
   can yield meaningful speedup through better overlap, even without bucketed prefetch.

3. ANALYSIS
──────────────────────────────────────────────────────────────────────────────

A. Suspicious zero-2 no-PP throughput split (12 905 vs 13 703 tok/s)
   Only zero-2 no-PP shows ~6% imbalance between DP ranks; zero-1 and zero-3 are
   symmetric. Likely a single-iter startup artifact affecting the per-iter timing
   average (only 5 iters, no re-run). Should be re-run for clean data.

B. PP=2 non-bucketed: all configs ~28k tok/s per DP-rank
   All four configs are within 2% of each other (27 933–28 201 tok/s per DP rank).
   ZeRO overheads are now fully overlapped with computation at PP=2. The throughput
   gap between ZeRO stages was already small in Run 2; it is now essentially noise.

C. Bucketing hurts throughput at PP=2 (~10–14% regression)
   Non-bucketed PP=2 dp-nozero reaches 55 073 global tok/s vs 48 927 bucketed — an
   11% drop. This is consistent across all ZeRO levels. The cost is DAG overhead from
   dispatching 36× more fine-grained FWD/BWD tasks through the scheduler, plus
   per-bucket NCCL calls that don't saturate the NIC individually. For this model size
   and batch configuration, bucketing is a net negative without ZeRO.

D. No-PP ZeRO-3 is fastest (29 017 global tok/s, +11.5% over dp-nozero)
   This repeats the Run 2 finding for ZeRO-1 (+13.9%) but with ZeRO-3 winning this
   time. The margin is within run-to-run noise. The RS+AG pattern is competitive with
   plain all-reduce at DP=2 because RS and AG are individually ~half the all-reduce
   volume and both fit within the synchronization window.

4. COMPARISON TO PREVIOUS RESULTS (baseline_comparison.txt)
──────────────────────────────────────────────────────────────────────────────

The most striking change is the 3.5–4.2× throughput increase across all configs.
This is entirely explained by the removal of torch.autograd.set_detect_anomaly(True)
in the dag-ir merge. That call was silently wrapping every forward op with Python-
level stack capture, dominating forward time (204ms → 17ms for the baseline forward
pass). It was not a real performance characteristic of the system.

  The slightly lower baseline speedup (3.54×) vs PP=2 runs (~4.1×) makes sense:

Relative ordering of ZeRO stages is unchanged: all stages within ~2% of each other
at PP=2. No-PP shows more variance between stages due to small absolute token count
per iter (4096 vs 16384), making per-call NCCL latency relatively more important.

Memory numbers are identical between Run 2 and post-merge (to within ±0.05 GiB),
confirming that the merge did not change any memory allocation paths.
